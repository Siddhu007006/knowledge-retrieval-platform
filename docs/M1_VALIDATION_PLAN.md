# M1.3–M1.4 — Ingestion and Retrieval Validation

## M1.3 ingestion checklist

| Format | Parser | Metadata retained | Automated coverage |
|---|---|---|---|
| PDF | PyMuPDF | Page numbers | Corrupt and empty PDF validation |
| DOCX | python-docx | Paragraph styles and table row locations | Paragraph/table extraction and malformed file tests |
| TXT | UTF-8 with fallback decoding | Paragraph boundaries | Basic extraction, empty file and paragraph tests |
| CSV | Python `csv` | Column names, row count and row locations | Header mapping and UTF-8 BOM tests |

All parsers feed the common normalization and chunking path. Chunk size and overlap are configurable through `CHUNK_SIZE` and `CHUNK_OVERLAP`.

## M1.4 evaluation dataset

| Domain | Included source | Query types |
|---|---|---|
| HR policy | Leave, sick leave, parental leave and onboarding policy | Factual, procedural, comparative, unavailable-information |
| IT Support | Password reset, VPN, software installation and hardware support | Factual, procedural, comparative, unavailable-information |

The labelled query set is `backend/evaluation/datasets/queries.json`.

## Retrieval metric

For answerable query set Q and K ∈ {1, 3, 5}:

`Hit@K = (number of answerable queries with at least one labelled relevant chunk in first K results) / (number of answerable queries)`

Hit@K is also referred to as Top-K retrieval accuracy in the milestone report. The dataset labels specific evidence phrases, and the evaluation runner maps those phrases to chunk IDs. This measures whether the expected evidence chunk appears in the first K results; it does not measure the quality of the generated answer.

Unavailable-information queries are deliberately labelled with no relevant source document. They are reported separately so their expected behavior is abstention rather than successful retrieval. Answer grounding and the insufficient-context route must be reviewed for those queries.

## Run the evaluation

```bash
cd backend
# Set GEMINI_API_KEY in .env first
python scripts/evaluate_retrieval.py
```

Expected output contains:

- Total query count and answerable/unanswerable counts.
- `top_1_accuracy`, `top_3_accuracy`, and `top_5_accuracy`.
- Per-query chunk retrieval order, ranked document/chunk metadata, relevant chunk IDs, low-relevance results, domain, category, and expected behavior.

The runner writes `backend/evaluation/results/retrieval_evaluation.json`. Generated results and runtime indexes are excluded from Git.

## Interpretation and limitations

- If Top-1 is low but Top-5 is materially higher, relevant evidence is in the candidate set but initial ordering/reranking needs tuning.
- If Top-5 is low, inspect extraction quality, chunk boundaries, embedding suitability, and query formulation.
- A high Hit@5 does not guarantee grounded generation; citation correctness and answer grounding must also be checked.
- Unanswerable queries must not be treated as normal retrieval success cases. Verify that context filtering and response generation abstain when no evidence supports an answer.
- The runner resets only `backend/data/evaluation/` before each run so evaluation data stays isolated from documents uploaded through the application.

## M1.4 execution status and M2 proposals

The repository includes the two-domain corpus, labelled query set, chunk-level evidence mapping, metric implementation, and evaluation runner. Dataset-label checks confirm that all six answerable queries map to source chunks. Live Top-1/Top-3/Top-5 values must be generated by running the evaluation command with a configured Gemini API key; no retrieval scores are hard-coded or claimed in this repository.

Proposed improvements for Milestone 2, to be prioritized after reviewing the generated report:

1. **Chunking calibration:** adjust chunk size and overlap for cases where the relevant evidence is split across chunks or fails to reach Top-5.
2. **Hybrid retrieval:** evaluate lexical retrieval alongside vector similarity when exact identifiers, product names, or policy terms are missed.
3. **Reranking evaluation:** compare the current embedding-based reranker with a dedicated cross-encoder or another independently evaluated reranking method.
4. **Extraction quality:** add OCR only if scanned PDFs appear in the target knowledge base; add explicit table-layout tests for complex DOCX and CSV content.
5. **Answer-level evaluation:** measure citation correctness, answer faithfulness, and abstention quality separately from retrieval Hit@K.
6. **Clarification and memory evaluation:** add a labelled set of conversational follow-ups, ambiguous questions, and unrelated-session checks.

These are proposals, not completed Milestone 1 features.
